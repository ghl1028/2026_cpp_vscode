## Q1. Board::setCell에 경계 검사가 없으면 어떤 문제가 생기는가?
private 멤버와 inBounds 검사가 *함께* 있어야 캡슐화가 완성되는 이유를 설명하시오.

> 배열의 범위를 초과한 위치에 접근하면 예상하지 못한 메모리 영역을 수정하게 되어 프로그램이 오작동하거나 런타임 오류가 발생할 수 있습니다. 
> private 멤버만으로는 외부 접근을 막을 수 있지만, 공개 메서드 setCell() 내에서 경계를 검사해야 내부 상태의 불변성을 보장하고 안전한 캡슐화를 완성할 수 있습니다.

## Q2. const GameState& state를 받는 함수에서 state.board.setCell(...)을 호출하면 컴파일 에러가 나는 이유는?
Day 1에서는 같은 실수가 왜 에러 없이 통과됐는가?

> const 참조 파라미터는 객체의 상태 변경을 컴파일 단계에서 방지합니다. setCell()은 비상수 메서드이므로 const 객체에서 호출할 수 없습니다. 
> Day 1은 직접 배열 원소에 접근했으므로 const 정확성이 적용되지 않았으나, Day 2의 클래스 기반 설계는 메서드 호출을 통해 상태 변경을 제어하므로 const 규칙이 강제됩니다.

## 구현 중 막혔던 부분

| 증상 | 원인 | 해결 |
|------|------|------|
| 배열 밖의 위치에 값을 쓸 때 프로그램이 이상해짐 | setCell()에서 경계 검사가 안 됐음 | 모든 배열 접근 전에 inBounds() 확인 후 진행 |
| const state에서 setCell() 호출하니까 컴파일 에러 | 상태를 바꾸는 메서드는 const 객체에서 못 씀 | 읽기만 하는 메서드에 const 붙이고, 쓰기 메서드는 따로 분리 |
| [y][x] vs [x][y] 헷갈림 | 2D 배열 인덱싱 순서 혼동 | 위치(y)를 먼저, 그 다음 가로(x) → cells_[y][x] |
| Position 구조체를 쓰는 게 번거로움 | x, y 따로따로 쓰는 것보다 못하다고 생각 | {x, y} 한 번에 넘기니까 실제로 더 편함 |
